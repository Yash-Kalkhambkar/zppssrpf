# Supabase Storage integration for admin image uploads

Admin dashboard redesigned to hide image URLs from non-technical user (school principal). Image upload system moved from URL entry to file upload with Supabase Storage. All six tabs preserved (Notices, Highlights, History, Photos, Admissions, Messages) with improved UX for elderly principal.

**Watch for:** getPublicUrl API shape mismatch (confirmed), missing ImageUpload import causes build failure (confirmed), missing uploadAndUpdateImage destructuring causes build failure (confirmed), missing aria-live on upload status (confirmed), RLS allows any authenticated user to upload (likely acceptable for dedicated project).

**Verdict**: NEEDS_CHANGES

## High-level view

The image upload implementation correctly uses the Supabase Storage client for file operations, but getPublicUrl returns `{ data: { publicUrl } }` and the code extracts `data.publicUrl` which would be undefined. ImageUpload and uploadAndUpdateImage are used in Admin.tsx but never imported, which will fail TypeScript compilation. The admin dashboard successfully hides URLs from the user and provides drag-and-drop file upload with preview and progress feedback. Confirmation dialogs appear before deletions across all CRUD sections. All existing functionality is preserved across the six tabs with improved plain-language messaging for non-technical users. The setup documentation provides SQL for RLS policies that correctly gates uploads to authenticated users while allowing public read access.

## getPublicUrl API shape mismatch

imageUpload.ts lines 30-34 call `supabase.storage.from('school-images').getPublicUrl(filePath)` and destructure `{ data: urlData }`, then return `urlData.publicUrl`. The Supabase Storage API returns `{ data: { publicUrl } }`, not `{ data: publicUrl }`. The current code would return `undefined` as the URL, causing updateImage to write undefined to the database and breaking image display.

The correct extraction is:

```typescript
const { data: { publicUrl } } = supabase.storage
  .from('school-images')
  .getPublicUrl(filePath);

return {
  success: true,
  url: publicUrl
};
```

## ImageUpload component missing from Admin imports

Admin.tsx line 313 renders `<ImageUpload />` inside ImageSettings, but the import block at the top doesn't include ImageUpload from '../components/ImageUpload'. This will fail TypeScript compilation with "Cannot find name 'ImageUpload'".

## uploadAndUpdateImage missing from useData destructuring

Admin.tsx line 20 destructures `images` from `useData()`, and line 306 (inside ImageSettings) destructures `{ images, uploadAndUpdateImage }` again. But uploadAndUpdateImage is never imported in the outer destructuring, so the inner one references undefined. The function exists in DataContext (line 37 of the interface, lines 283-323 of the implementation), but Admin.tsx needs to pull it from the context.

## Test coverage gap

The implementation has no automated tests for uploadImage, deleteImage, or the orchestration in uploadAndUpdateImage. The ImageUpload component's drag-and-drop handlers and file validation logic are untested. The getPublicUrl bug would have been caught by a unit test that mocked the Supabase response and verified the returned URL.

## Accessibility: missing aria-live on upload status

ImageUpload shows success and error messages without aria-live regions, so screen readers won't announce upload completion or failure until the user navigates back to the message. Add `aria-live="polite"` to the error message div at line 151 and to the success toast that shows after upload completes.

## Storage RLS: any authenticated user can upload

STORAGE_SETUP.md lines 21-43 provide RLS policies that gate uploads on `auth.role() = 'authenticated'` but don't verify the user is an admin in the school's system (e.g., checking a role column in a profiles table). Any authenticated Supabase user could upload to this bucket. If the Supabase project is dedicated to this school and only admin accounts exist, this is acceptable. If the project is shared or might have non-admin authenticated users in the future, this is a security hole.
