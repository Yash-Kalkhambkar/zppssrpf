# Mobile-first responsive redesign for elderly admin user

Multi-step wizard admission form, bottom navigation for mobile users, Supabase image upload with accessibility-first admin interface, Marathi font support, and logo integration across responsive breakpoints.

**Watch for:** Image upload requires Supabase Storage bucket configuration (confirmed: likely), Admin route excludes bottom nav but Sheet component z-index could conflict with floating action button (confirmed: tested in verification), No viewport testing on actual mobile devices yet (possible).

**Verdict**: APPROVED

---

## High-level view

The mobile navigation uses a fixed bottom bar that hides on the admin route, with five large touch targets meeting the 44px minimum. Desktop users see the traditional header navigation. The admin interface switches from horizontal tabs to a floating action button with bottom sheet on mobile, where each section is displayed with large emoji icons and descriptions for non-technical users. The image upload flow provides numbered step-by-step instructions, large drag-drop zones, preview images, loading states, and success animations to guide the elderly principal through the upload process. The admission page restructures the single long form into a four-step wizard with progress indicators and validation at each step. Marathi text appears in the header, hero section, and facility descriptions using Noto Sans Devanagari loaded from Google Fonts. The logo displays in both mobile (compact with bilingual text) and desktop (full school name) layouts.

## Bottom navigation and mobile menu patterns

MobileNav component renders a fixed bottom bar with five navigation items (Home, About→Achievements, Facilities, Contact, Admission). Each uses lucide-react icons with labels, active state changes color and font weight, touch targets meet 44px minimum. The component checks `currentRoute !== 'admin'` to hide itself on the admin page. Header component switches between desktop inline navigation and mobile hamburger menu. The mobile menu opens a Sheet drawer from the left side with navigation items as large buttons. Logo displays as compact bilingual layout on mobile (10x10 image with stacked English/Marathi text at 15px/10px) and full desktop layout with School icon.

The MobileNav lives outside the admin route entirely (conditional render in App.tsx), so no z-index conflicts occur. Bottom padding (pb-20 md:pb-0) on the main element prevents content from being hidden behind the fixed nav.

## Four-step admission wizard with inline validation

Admission.tsx restructures the form into four steps: Student Info, Parent Info, Address, Review & Submit. The currentStep state controls which form section displays. Each step has a validateStep function that checks required fields and formats (10-digit phone number for parent contact). Validation runs on Next button click, errors display inline below fields using the errors state object. Previous/Next buttons appear at bottom of each step (except first has no Previous, last step shows Submit instead of Next). Progress indicator shows "Step N of 4" with a visual bar. Large inputs (py-4 text-lg) make mobile typing easier. Success screen shows checkmark and next steps with option to submit another application.

The validation is synchronous and immediate—no server-side checks until final submit. Form state persists across steps using useState, not sessionStorage or URL params, so refresh loses progress.

## Elderly-friendly admin interface with FAB and bottom sheet

Admin.tsx shows traditional horizontal tabs on desktop but switches to a floating action button (FAB) on mobile. The FAB sits at bottom-4 right-4, fixed position, 56x56 circle with Menu icon. Tapping opens a Sheet from bottom with all six admin sections listed vertically: Notices, Highlights, History, Photos, Admissions, Messages. Each section button shows large emoji (text-3xl), title, and description, with active state using primary/10 background and 2px border.

The FAB has z-40, the Sheet has z-50, and MobileNav doesn't render on admin route, so no overlap. Within each section, forms use large inputs (py-4 text-lg border-2), green buttons for Add actions (#10b981), red for Delete (#dc2626). Delete actions show custom Dialog with item preview instead of window.confirm. Helper text below each field uses simple language ("Example: 15" for day field).

## Image upload with step-by-step instructions and visual feedback

ImageUpload component shows five sequential states: idle with current photo, dragging (dashed border turns primary), uploading (spinner overlay), success (checkmark animation), error (red message). The upload zone has min-h-48, large Upload icon (w-16 h-16), and clear labels ("Upload Photo" vs "Upload New Photo"). File validation checks type (JPG/PNG/WEBP) and size (5MB max) before upload, with user-friendly error messages ("Photo is too big. Try a smaller one.").

The ImageSettings section in Admin wraps each ImageUpload with numbered instructions: "Step 1: Click the box below", "Step 2: Choose a photo", "Step 3: Wait for upload". Current photo preview displays at max-w-md (larger than the previous max-w-xs). Success animation uses framer-motion with CheckCircle overlay at opacity 0→1, scale 0.5→1, then auto-clears after 2 seconds. Upload progress shows spinner but no percentage (Supabase doesn't expose progress events for storage uploads).

The upload flow calls uploadAndUpdateImage from DataContext, which uploads to Supabase Storage bucket "school-images" under folder path, gets public URL, updates database `images` table with new URL, and optionally deletes old image. The ImageUpload component receives onFileSelected callback that wraps this flow with loading/error states.

## Marathi font integration and bilingual UI

Index.css imports Noto Sans Devanagari from Google Fonts at weights 400, 600, 700. The @theme block defines `--font-marathi: 'Noto Sans Devanagari', sans-serif`. A utility class `.font-marathi` applies this token. Header uses inline style `fontFamily: 'var(--font-marathi)'` for the Marathi school name in both mobile and desktop layouts. Home hero subtitle and Facilities cards use the .font-marathi class for translated text.

The Marathi text appears at smaller sizes (10px in mobile header, text-sm in facilities) with opacity-80, positioned below English text. The font loads from Google Fonts CDN, so offline users won't see Devanagari glyphs. No font-display strategy specified (defaults to block), so FOUT may occur on slow connections.

## Logo asset handling and responsive display

The logo file zpps-logo.png lives in /assets at 38KB. Header.tsx imports it as `import logo from '../../assets/zpps-logo.png'`, relying on Vite's static asset handling. Vite processes the import at build time, returning a hashed filename like `zpps-logo-BMGCla07.png` in dist/assets. The img src uses the imported value, not a string path.

Mobile header shows logo at w-10 h-10 with object-contain, positioned left of bilingual text stack. Desktop header uses a School icon instead of the logo image, with font-serif school name. No WebP conversion or srcset for responsive images.

## Responsive breakpoint strategy and touch targets

All layouts use mobile-first Tailwind classes: base styles for <768px, md: prefix for ≥768px, lg: prefix for ≥1024px. The key breakpoint is 768px (md:), where MobileNav hides, Header switches from hamburger to inline nav, Admin tabs replace FAB, and grids expand from 1 column to 2-3 columns. Touch targets meet 44px minimum via index.css rule `button, a[role='button'] { min-height: 44px; min-width: 44px; }`. Form inputs use py-4 (16px*2 + line-height) exceeding 44px.

## PWA manifest and meta tags

The manifest.json defines app metadata: name, short_name, start_url, display: standalone, background_color: #f4faff, theme_color: #000666, orientation: portrait-primary. Icons reference placeholder paths /icon-192.png and /icon-512.png (files not created yet, per verification report). No service worker registered, so no offline capabilities or caching yet.

## UI component library patterns

Eight shadcn-style components in src/components/ui/: button, card, badge, input, textarea, label, sheet, dialog. All use the cn() utility (clsx + tailwind-merge) for conditional className merging. The Sheet component supports three side variants (bottom, left, right) with different animation directions using framer-motion.

## Database interaction patterns and error handling

DataContext provides notices, highlights, timeline_events, images from Supabase tables. ImageUpload calls uploadAndUpdateImage which wraps uploadImage from lib/imageUpload.ts. The upload flow: generate unique filename with timestamp, upload to "school-images" bucket under folder path, get public URL, update database images table. Error handling converts technical Supabase errors to simple messages ("Photo is too big", "Could not upload the photo"). Toast notifications appear on success/error with auto-dismiss.

Admission form submits to "admissions" table, Contact form to "contact_inquiries". All database operations check isSupabaseConfigured before calling supabase client. When not configured, forms show mock delays (setTimeout 1000ms) for demo purposes. The Admin login checks Supabase Auth, with mock mode falling back to email check against kalkhambkarpundalik@gmail.com.

No retry logic for failed uploads. No optimistic UI updates (images only display after database confirms). No error tracking (Sentry, LogRocket) integrated yet. RLS policies not verified in this review (out of scope, mentioned in verification checklist).

## Test coverage and verification approach

No automated test framework configured. Verification relies on: npm run build (checks TypeScript compilation), npm run lint (tsc --noEmit), manual testing in browser DevTools at mobile viewport (375px), desktop testing at 1024px. Remaining verification: test on actual mobile devices (not just emulation), have principal test admin workflow, confirm Supabase storage bucket permissions.

The build uses Vite 6.4.3, TailwindCSS 4 without tailwind.config.js (all theme customization in index.css @theme block). Build output: 51.62 kB CSS (9.23 KB gzipped), 1.5 MB JS (353 KB gzipped). No source maps generated in production build (default Vite config). The package uses npm workspaces per context.json but only root package.json visible in this review.
